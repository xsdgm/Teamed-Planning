# v9 三机／四机受控验证

后续对入口选择回归的修复与验证见 [入口选择修复报告](v9_fleet_entry_repair_20261111.md)。本文保留上一轮对照结果。

本次固定 best576 学习策略，检查四机验证中初始化、随机数、车端导航及执行审计的干扰。
没有重新训练、调整奖励、放宽 CBF、增加任务预算或改变 2 米到达标准。

## 实现

- [验证入口](validate_v9_fleet_controlled.py) 为每个任务启动独立进程，冻结运行源码、权重、配置及场景；不同运行版本不会复用 Python 模块缓存。
- [配对控制](fleet_controlled_support.py) 保留前三架的原始位置，在车辆 `(27, 18)` 米相对位置增加第四架。不会因机数改变而镜像前三架；边界不允许该布局时明确报错。
- 动作随机数按采样种子、无人机身份、仿真步索引。增加第四架不会消耗前三架的噪声序列；相同噪声不意味着在不同观测下强制相同动作。
- 通信丢包、时延和同一到达时间的消息顺序按发送端、接收端、发送步配对。仍保留原有 10% 丢包、0–2 步附加延迟和至少一跳一秒的协议。
- 归档组使用历史完整运行环境；修复组仅替换清单中的车端导航、融合和同一感知范围内的精细局部传感器。无人机 Actor、建图、输入编码、奖励和独立 CBF 保持归档版本。
- 入口默认运行归档／修复两个组，显式比较其收益和回归；不会把一次修复组成功自动推广为正式运行环境。
- 车端收到明确的 `motion_held` 标志。主动等待时继续感知、融合和规划，输出零运动，不累计导航停滞时间；放行后真实停滞仍触发恢复。
- 每步独立审计车辆圆形障碍扫掠、无人机间相对运动最小距离和所需无线链路端点距离。CBF 拒绝时另解二维半平面最小速度，区分约束真无解和优化器误判。

生产代码中的等待修复见 [GroundRobotController](../../../src/teamed-planning/scripts/ground/ground_main.py)，
专项回归见 [test_motion_hold.py](../../../src/teamed-planning/scripts/tests/ground/test_motion_hold.py)。
外部调用者主动抑制车辆运动时应传入 `motion_held=True`；缺省行为保持原样。

## 复现

在仓库根目录使用 `teamedplanning-2d` 环境：

```bash
python -I -B experiments/mappo/v9/test_v9_fleet_controls.py
python -I -B src/teamed-planning/scripts/tests/ground/test_motion_hold.py
python -I -B experiments/mappo/v9/validate_v9_fleet_controlled.py \
  --output artifacts/v9-fleet-controlled-new-run \
  --runtimes archived candidate --samples 3 --workers 6
```

查询进度会核验进程启动标识，而非直接相信旧的 `running`：

```bash
python -I -B experiments/mappo/v9/validate_v9_fleet_controlled.py \
  --output artifacts/v9-fleet-controlled-final-20261111 --status
```

这些是三个指定场景上的重复采样。应比较相同布局和随机协议下的新旧组，不能把先前默认四机的 5/9 与新组直接当作单一修复的因果增益。
其中 `repaired` 现已固定为本报告的上轮修复参考，`candidate` 使用当前车端代码。
车辆到达、已交付地图连通和安全约束可行是不同指标；车辆恢复规划可以独立贡献到达，因此到达率不能单独证明无人机策略优劣。
